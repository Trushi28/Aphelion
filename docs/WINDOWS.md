# Windows executor

Aphelion is not POSIX and does not try to be. Running Windows programs is a separate layer: a clean-room executor that loads PE images and answers their calls with Aphelion's own primitives. It is built in stages, and each stage is host-tested before anything runs in ring 3.

Licence rule for this layer: ReactOS, Wine, Sogen and NeptuneOS are behaviour references only. Their source is not read and no code is copied. Documented behaviour (Microsoft's published PE format and API contracts) and observation of real binaries are the inputs.

## W1: the PE loader (`kernel/include/cosmos/pe.hpp`)

A pure header with no kernel dependencies, namespace `pe`. It never allocates. The kernel, a host tool and the tests all use the same code.

| Function | What it does |
| --- | --- |
| `parse(file, size, &image)` | Validates every header, section and directory the loader will later touch and fills an `Image` (about 8 KiB, fits on a stack). On any failure the image is zeroed. |
| `plan(image, runs, cap)` | Merged page runs: headers read-only, each section at its own protection, gaps read-only. Returns the full count even when `cap` is smaller. |
| `map(image, file, size, buffer, bytes)` | Copies headers and section data into a zeroed flat image buffer of `size_of_image` bytes. |
| `relocate(image, buffer, base, &applied)` | Applies DIR64, HIGHLOW and ABSOLUTE relocations for a 64 KiB-aligned base. |
| `bind_imports(image, buffer, resolver, ctx, &report)` | Resolves every import by name or ordinal. Two passes: nothing is written to the IAT unless everything resolved. |
| `tls_info(image, buffer, base, &tls)` | Template, zero fill, index slot and callback list, as absolute addresses for the stated base. |

### What is accepted

- PE32+ for x86-64 only. PE32 and i386 return `Pe32Unsupported`; a CLR directory returns `ManagedUnsupported`.
- Section alignment a power of two from 4096 to 1 MiB and at least the file alignment; file alignment a power of two from 512 to 65536.
- At most 96 sections and 16 MiB of image. The preferred base must be 64 KiB aligned and below the user limit.
- Section addresses ascending and aligned; raw data aligned, inside the file, outside the headers and non-overlapping.
- Every directory (except Security, which is a file offset) lies inside one section or the headers.
- The entry point is inside an executable section. A DLL may have none.

### What is refused, on purpose

- A section that is both writable and executable (`WritableExecutable`). Windows allows it and some packers rely on it; Aphelion keeps W^X unconditional.
- Relocation entries that touch the headers, gaps, or cross the end of a section.
- Images that cannot move at any base other than the preferred one (`NeedsFixedBase`). An image can move when it is not marked relocation-stripped and either has a relocation table or sets the dynamic-base flag. An image with the dynamic-base flag and no table is position independent: it moves with nothing to patch (`applied` is 0). This is what GNU ld emits for small freestanding programs.
- A TLS callback outside executable memory.

### Missing imports

`bind_imports` returns `UnresolvedImport` and fills an `ImportReport`: counts of libraries, imports, resolved and missing, plus the first 32 missing entries with DLL name and function name or ordinal. The loader refuses to run the program and names the function, rather than starting it and crashing later through a null import slot. The resolver is called once per import in each pass.

### Tests

`make test-pe` builds `tools/pe_host_test.cpp` with ASan and UBSan. It contains:

- a synthetic PE builder (four sections, imports, TLS, exceptions, relocations), about fifty directed malformed-header cases that each check the exact status, and a second builder for the limits (section count, alignments, image size, the user-limit boundary);
- 4000 random section layouts checked against an independent invariant function and an independent page-plan checker;
- every truncation of the sample images, byte-value sweeps over every header byte, table sweeps over the import, TLS and relocation tables with an exact-size image so ASan sees any overrun, and 300,000 random multi-field header rewrites;
- four real images linked by `lld-link` (`tools/pe-samples/`, regenerated by `build.sh`, embedded as base64 in `tools/pe_samples.hpp`): a console program with TLS and a pointer table, the same program fixed-base, a program importing by name and by ordinal from an import library, and a DLL;
- two real images linked by GNU ld through MinGW-w64 gcc (`embed-mingw.sh`, embedded in `tools/pe_samples_mingw.hpp`): a freestanding program that imports three functions from `kernel32.dll` and has no relocation table, and a stripped `printf` program (47 relocations, 47 imports from `kernel32.dll` and `msvcrt.dll`, two TLS callbacks, a `.CRT` section). They are checked for parse, relocation, binding, a refused `msvcrt.dll`, TLS callbacks and every single-byte mutation of the small one.

Mutation check: 348 single-token mutants of `pe.hpp` (comparison operators, `&&` and `||`, `+` and `-`, and every early `return Status::X` replaced by `Ok`) were run against the suite under ASan and UBSan with `-fno-sanitize-recover=undefined`. 323 are killed. The other 25 are equivalent: the changed bound is guarded by another check (for example `size <= 64` in `parse`, where a 64-byte file fails the PE offset check anyway), the array past `directory_count` is always zero, or the changed value only affects an empty copy. The first round of the check found gaps at the exact limits (96 sections, 255-character names, 256 libraries, 32767 imports, 16 TLS callbacks, 33 missing imports, empty relocation blocks, a plan into a short buffer) and a real bug: `plan` read past a short output array when merging runs. Each now has a directed test.

The relocation rule added after the first MinGW run (`relocatable` in `Image`) has its own 9-mutant check, all killed.

A differential run against `pefile` on lld output (default alignment, `/align:65536 /filealign:4096`, `/filealign:1024`) agreed on image base, entry, sizes, section table, protections, imports and relocation counts. That check is not part of `make test-pe`, because it needs Python and `pefile`.

### Limits

- Nothing in the kernel includes `pe.hpp` yet. W1 is the parser and loader logic only; W2 is the first user.
- The MinGW images are built by one gcc version; their bytes are embedded, so the tests do not depend on a toolchain, but regenerating them with another version will change the images and may change the counts the tests assert.
- Exports, forwarders, delay imports, bound imports, resources, the load config directory and exception unwinding data are validated for position only. W5 reads exports when DLLs are loaded.
- 32-bit PE files are refused, not emulated.
- The samples are produced by one linker (lld). Binaries from MSVC, MinGW or packers have more variety; the sweeps cover malformed input, not every legitimate layout.

## W2: the PE host (`userland/pehost`)

A Windows program runs inside an ordinary Aphelion process: `pehost.apx` is the process, the PE image is mapped into its address space, and the program's imports point at host functions. The kernel knows nothing about PE. The launcher gives the host one handle, a file with the Read and Delegate rights, as its argument.

Load sequence (`host.hpp`, header-only, no libc, identical in the kernel build and the host test):

1. `pe::parse`, then refuse DLLs (`STATUS_INVALID_IMAGE_FORMAT`) and images that cannot move (`STATUS_CONFLICTING_ADDRESSES`).
2. Map the image into a memory object at a 64 KiB aligned base, `pe::map`, `pe::relocate` to that base, `pe::bind_imports` against the host's table. Any missing import is logged by DLL and name (ordinals as `#n`) with a count, and the program does not start (`STATUS_ENTRYPOINT_NOT_FOUND`).
3. Read the TLS directory, then allocate a support block: two TEB pages (the Windows TEB is larger than one page and `TlsSlots` sits at 0x1480), a PEB page, the TLS pointer array and one TLS block (template copied, zero fill left zero, the module's TLS index slot set to 0).
4. Allocate a stack of the image's reserve size, clamped to 64 KiB to 1 MiB, and fill TEB stack base and limit.
5. Set the page protections from `pe::plan`: headers and read-only data R, code R+X, data RW. Everything is mapped RW until the imports are bound and the relocations applied, so a section that is read-only at run time can still be patched.
6. Point GS at the TEB, switch to the new stack, call each TLS callback with reason 1 (process attach), then call the entry point with the PEB address in `rcx`. A program that returns uses its return value as the exit status.

Exit statuses use the NT codes a Windows loader would report: `0xC000007B` bad image, `0xC0000018` conflicting addresses, `0xC0000017` no memory, `0xC0000139` entry point not found.

TEB fields set: `StackBase` 0x08, `StackLimit` 0x10, `Self` 0x30, client process (1) and thread ids 0x40 and 0x48, `ThreadLocalStoragePointer` 0x58, `ProcessEnvironmentBlock` 0x60, `LastErrorValue` 0x68, `TlsSlots` 0x1480 (64 entries). PEB fields set: `ImageBaseAddress` 0x10 and `ProcessHeap` 0x30; the rest of the page is zero. The layouts come from Microsoft's published documentation of these structures; only the fields above are populated and a program that reads another field sees zero.

Each host function has the Microsoft x64 calling convention (`ms_abi`). W2 provided `ExitProcess`, `GetStdHandle`, `WriteFile` (standard output and error go to the serial console), `GetLastError` and `SetLastError`; W3 added the rest, below.

### Tests

`make test-pehost` builds `tools/pehost_host_test.cpp` with ASan and UBSan (`-fno-sanitize-recover=undefined`) and runs real Windows programs natively on the Linux x86-64 test machine: the host loader runs in a forked child, GS is pointed at the TEB with `arch_prctl`, the stack is switched, and the program's `ExitProcess` and `WriteFile` land in host stubs that report through pipes. Because the stubs and the loader are the same files the kernel build uses, a pass here exercises the code that runs in ring 3.

| Program | Linker | What it proves |
| --- | --- | --- |
| `console.exe` | lld | relocated pointer table (7 relocations), TLS data through `gs:[0x58]`, `WriteFile`; exits with 9 |
| `k32.exe` | GNU ld (MinGW) | no relocation table, moves with nothing to patch; prints `Hello World` |
| `teb.exe` | lld | from inside the program: TEB self pointer, PEB image base, stack bounds, TLS array, process id, entry stack alignment (8 mod 16) |
| `tlscb.exe` | lld | two TLS callbacks run before the entry with the module base and reason 1; TLS data starts initialised, zero fill is zero, both are writable |

Refusals are tested with a fixed-base image, a DLL, an image with missing imports by name and by ordinal, the MinGW `printf` program (its 34 `msvcrt` imports are named), truncated and empty files. A dry-run platform records every protection call and every call into the program, and the test checks that the protections tile the image exactly with no writable executable run, that the entry and callbacks lie in executable runs, that the TEB and PEB are consistent and that the TLS block equals the template. That check runs on 480,000 single-byte mutations of four programs and 120,000 random multi-field header rewrites (a quick mode, `-q`, runs a tenth of the sweeps): each mutated image either fails with one of the five statuses or loads consistently. Failing each allocation and each protection call in turn is also checked.

The kernel boot self-test runs the same four programs through `pehost.apx` from the RAM realm and checks their exit statuses, and checks that a text file and an APX image handed to the host are refused with `0xC000007B`.

### Limits

- The Windows program and the host share one address space and one privilege level. The host stubs are reachable by any pointer the program holds; there is no isolation inside the process, and none is intended for W2.
- One thread. No `CreateThread` and no thread-start TLS callbacks. `TlsAlloc` exists (W3) but there is only ever one thread's slots.
- No structured exception handling and no unwinding. A fault in the program is a fault in the process and kills it with the kernel's fault status.
- `ProcessParameters` in the PEB is null: a program that reads it directly instead of calling `GetCommandLine` sees nothing. The environment is empty.
- Input is not implemented: `GetStdHandle` returns a handle for standard input but `WriteFile` accepts only standard output and error.
- Each protection run is a separate mapping, and a process has 64 mappings. An image whose sections need more than about 60 separate runs fails to load (`STATUS_NO_MEMORY`, with the reason logged).
- The image is placed at a fixed address, `0x100100000000`. DLL loading (W5) will need an allocator.
- The test machine must be Linux x86-64: the host test uses `fork`, `arch_prctl` and the Microsoft calling convention directly.

## W3: kernel32 and msvcrt subsets, so a MinGW program runs

The MinGW `hello world` (`x86_64-w64-mingw32-gcc new.c -o hello.exe`, 47 imports) now runs unmodified, in the host test and inside the kernel. The pieces, all header-only and free of libc so the host test and the ring-3 build compile the same text:

| File | Contents |
| --- | --- |
| `heap.hpp` | `Heap`: boundary-tag allocator, 16-byte alignment, first fit, coalescing, in-place grow and shrink, `check()` for the invariants. Memory comes from the platform in chunks (256 KiB doubling to 2 MiB, at most 8 chunks, 8 MiB in all). Pointers it did not hand out, interior pointers and double frees are refused, not acted on. |
| `codec.hpp` | UTF-8 to UTF-16 and back. Lenient mode replaces each maximal ill-formed subpart with U+FFFD; strict mode fails. |
| `format.hpp` | The `printf` core: flags `-+ #0`, width and precision (also `*`), `hh h l ll z t j I I32 I64`, and the conversions `d i u o x X c s p %`. `%p` is 16 upper-case hex digits as msvcrt prints it. Floating point (`f e g a`) and `n` are not supported: the call returns -1 and sets `errno` to `EINVAL` instead of printing something wrong. |
| `cmdline.hpp` | Splits a command line by the Microsoft rules (program name up to the first space or closing quote, then backslashes before quotes, doubled quotes inside quotes). |
| `win32.hpp` | `kernel32.dll`: process (`ExitProcess`, `TerminateProcess` on the current process, `GetCurrentProcess`, `GetCurrentProcessId`, `GetCurrentThread`, `GetCurrentThreadId`), console (`GetStdHandle`, `WriteFile`), errors, heap (`GetProcessHeap`, `HeapAlloc`, `HeapFree`, `HeapReAlloc`, `HeapSize`), thread-local storage (`TlsAlloc`, `TlsFree`, `TlsGetValue`, `TlsSetValue`, 64 slots in the TEB), critical sections (five calls; there is one thread, so they count and never block), modules (`GetModuleHandleA/W`, `GetProcAddress`, `GetModuleFileNameA`, `GetCommandLineA/W`), memory protection (`VirtualQuery`, `VirtualProtect`, image pages only), `Sleep`, `SetUnhandledExceptionFilter`, and the code-page calls (`MultiByteToWideChar`, `WideCharToMultiByte`, `IsDBCSLeadByteEx`, `GetACP`). |
| `msvcrt.hpp` | `msvcrt.dll`: the C start-up hooks (`__getmainargs`, `__set_app_type`, `__setusermatherr`, `_initterm`, `_initterm_e`, `_fmode`, `_commode`, `__initenv`, `_lock`, `_unlock`, `_amsg_exit`), `exit`, `_exit`, `_cexit`, `abort`, `atexit`, `_onexit`, `signal`, stdio on standard output and error (`__iob_func`, `fwrite`, `fputc`, `fputs`, `puts`, `putchar`, `fflush`, `printf`, `fprintf`, `vfprintf`, `vprintf`, `sprintf`, `vsprintf`, `_snprintf`, `_vsnprintf`), the allocator (`malloc`, `calloc`, `realloc`, `free`), string and memory functions, `getenv` (always unset), `strerror`, `localeconv`, `_errno`. |

How the time and process facts are obtained: there is no clock syscall, so no time function is provided. `Sleep` waits on the read end of a pipe nobody writes, with a timeout, which is the one way ring 3 can sleep today. The command line is fixed at `pe.exe` by the Aphelion host, because a process receives one handle and nothing else; a launcher that passes arguments is future work, and the host test passes real command lines through `--run`.

### Running a program on the test machine

`build/pehost_host_test --run program.exe ["command line"]` runs any PE the host accepts, natively on Linux x86-64, and prints its output and exit status. For example `build/pehost_host_test --run hello.exe` runs the 249 KB MinGW program. The host logs what it refused and why. A Windows program that needs something missing is refused with the import named, before any of its code runs.

### Running a program from the shell

In shell mode the bundled programs are installed in `ram:/apps` at boot: `hello` (a native APX program), `pehost` (the PE host itself), and the Windows test programs `console.exe`, `k32.exe`, `teb.exe`, `tlscb.exe`, `stdio.exe` (`printf("Hello World\n")`), `crt.exe`, `ucrt.exe` and `dyn.exe`, with the DLLs `dllmath.dll`, `dllchain.dll`, `dllplug.dll` and `dllfail.dll` that `dyn.exe` loads. `chart ram:/apps` lists them and `run stdio.exe` runs one: a file that starts with `MZ` is handed to `pehost`, anything else is launched as an APX image. The program's console output is printed in the shell (it also goes to the serial log with a `[user N]` prefix), Ctrl+C kills it, and the shell prints `exit status N`. Only plain names in `ram:/apps` are accepted. Programs cannot take arguments or read input yet, and the realm is in memory, so `ram:/apps` is rebuilt at every boot. To try your own program, copy it into the realm (for example with `twin disk:/prog.exe ram:/apps/prog.exe`) and `run prog.exe`.

### Tests

`make test-pehost` now builds two programs. `pehost_host_test` is the W2 one plus `stdio.exe`, `crt.exe` and `ucrt.exe`. `pehost_lib_test` (about 340 checks) covers the pieces:

- The heap against a model: 400,000 random allocate, free and resize operations with contents verified and no two live blocks overlapping, an invariant check every 997 operations, exhaustion and recovery, a failing or misaligned platform, double and foreign frees, and deliberate corruption of every kind of metadata to show that `check()` notices.
- UTF-8 against an independent encoder for all 1,112,064 scalar values, against an independent validity check on a million random byte strings, and (once, outside the test) against Python's decoder on 200,000 random inputs: identical output.
- `printf` against glibc: 600,000 random format and value combinations print the same text with the same return value.
- Command lines against the documented Microsoft examples, plus the storage and argument limits.
- Every kernel32 and msvcrt stub, including process exit, `abort`, exit-handler order and `_amsg_exit` in forked children, `memmove` and `memcmp` and the string functions against libc, and the import tables (no duplicates; every entry found by `GetProcAddress`).

`crt.exe` (MinGW, `__USE_MINGW_ANSI_STDIO=0` so `printf` comes from `msvcrt`) checks about forty behaviours from inside the program and returns 7 when all pass; `stdio.exe` is the plain `printf("Hello World\n")` program, built stripped (39 KB) and, in a manual check, unstripped (249 KB, the size of the user's `hello.exe`). The kernel self-test runs both on every disk configuration.

MinGW builds are made reproducible with `-Wl,--no-insert-timestamp` (the PE header otherwise carries the build time), so regenerating the samples gives identical files.

### Limits

- Floating-point `printf` conversions are not provided in `msvcrt`. A MinGW program built with its default stdio uses MinGW's own formatter and prints doubles correctly (checked with `%f %e %g`); one built with `-D__USE_MINGW_ANSI_STDIO=0`, or an MSVC program linked against `msvcrt`, calls `msvcrt`'s `printf`, which returns -1 and prints nothing for a `double`.
- Every code page is UTF-8. `WideCharToMultiByte` never substitutes a default character.
- `HeapReAlloc` with `HEAP_ZERO_MEMORY` zeroes the bytes from the old block's usable size, not from the size originally requested, because the allocator does not record the requested size; the bytes in between keep whatever they held.
- The heap never returns memory to the system, is capped at 8 MiB, and has no `HeapCreate`, `VirtualAlloc` or `LocalAlloc` (those imports are reported missing).
- `VirtualProtect` and `VirtualQuery` only know the program's own image, and a writable-and-executable request is refused. A program that needs the MinGW runtime's pseudo-relocations (auto-imported data from a DLL) is not supported, and none was available to test it.
- No standard input (`ReadFile`, `fgets`, `scanf`, `getchar` are missing imports), no files, no environment variables, no locale beyond `C`, no wide-character stdio, no `qsort` or `strtol` family, no time.
- No exceptions: `__C_specific_handler` always answers "continue search", so structured exception handling never handles anything.

## Inspecting a program: `make peinfo`

`build/peinfo [-v] [--supported docs/pe-supported.txt] program.exe` runs the loader on a real file and prints the headers, sections, relocation count, TLS, and every import grouped by DLL. It exits 0 when the image can run, 1 when the loader refuses it or it is fixed at a base Aphelion cannot map. With `--supported`, imports the executor does not provide are marked `MISSING`.

What a MinGW `hello world` needs: `x86_64-w64-mingw32-gcc new.c -o hello.exe` produces a 249 KB image with 47 imports. 13 come from `kernel32.dll` (critical sections, `Sleep`, `TlsGetValue`, `VirtualProtect`, `VirtualQuery`, `GetLastError`, `SetUnhandledExceptionFilter`, code-page conversion) and 34 from `msvcrt.dll` (`__getmainargs`, `__set_app_type`, `_initterm`, `_onexit`, `__iob_func`, `fwrite`, `vfprintf`, `malloc`, `free`, `signal`, and so on). W3 provides all of them.

## W4: what programs ask for and Aphelion lacks

Two pieces, both host tools, so no kernel change.

- `docs/pe-supported.txt` is the list of every `dll!function` the executor provides (171 today). It is generated from the executor's own import tables (`build/pehost_host_test --list-supported`, or `make pe-supported` to rewrite the file), so it cannot drift from the code: `make test-pehost` fails with "docs/pe-supported.txt is stale" if someone adds or removes a stub without regenerating it.
- `build/peinfo --coverage --supported docs/pe-supported.txt a.exe b.exe ...` scans any number of programs and prints, for each, whether it can run, then the missing imports ranked by how many of the programs need each one. That ranking is the work list: implement what the most programs ask for first. Running it over a folder of real programs (`peinfo --coverage --supported docs/pe-supported.txt ~/windows-tools/*.exe`) is the intended use; it exits 1 if any program is blocked.

The tests check the report on the bundled samples (seven runnable, plus `gaps.exe`, a MinGW program using `fopen`, `qsort`, `strtol` and `time`, which is reported with exactly those four gaps) and that the set peinfo reports for `gaps.exe` equals the set the real host logs when it refuses the program.

What it does not do: it counts imports by name only. It cannot tell that a supported function is called with an argument combination the stub does not handle (for instance `VirtualProtect` with a writable-and-executable request), so "all provided" means the program loads and links, not that it runs correctly. It also does not follow `LoadLibrary`/`GetProcAddress` at run time: a program that loads a library by a name built at run time is only discovered when it runs.

## W5a: API sets, `ucrtbase.dll` and built-in `LoadLibrary`

A program built against the universal C runtime (MSVC, or MinGW with `-D_UCRT -lucrt`) does not import `msvcrt.dll`. It imports about a dozen small "API set" names such as `api-ms-win-crt-stdio-l1-1-0.dll`, which Windows redirects to `ucrtbase.dll`. `ucrt.exe` in the samples is such a program (63 imports from nine names); W4's coverage report showed 32 of them missing before this step.

- `kernel/include/cosmos/pe_modules.hpp` holds the one rule for names, `pe::modules::canonical`: case-insensitive; `kernelbase.dll` is `kernel32.dll`; `api-ms-win-crt-*.dll` is `ucrtbase.dll`; any other `api-ms-win-*.dll` or `ext-ms-win-*.dll` is `kernel32.dll`; everything else is unchanged. The host's import resolver, `GetModuleHandle`/`LoadLibrary`/`GetProcAddress` and `peinfo` all use it, so a program cannot resolve by one rule and be reported by another.
- `ucrt.hpp` adds the `ucrtbase.dll` table. 38 entries are the same stubs `msvcrt` uses (same addresses): allocator, strings, `fwrite`/`puts`/`putchar`/`fflush`, `exit`/`_exit`/`_cexit`, `signal`, `_initterm`, `getenv`, `strerror`, `localeconv`, `_errno`. The other 34 are UCRT-only: `__acrt_iob_func`, `__stdio_common_vfprintf`, `__stdio_common_vsprintf`, `__stdio_common_vfwprintf` (fails with `EINVAL`), `_configure_narrow_argv`, `_configure_wide_argv`, `__p___argc`, `__p___argv`, `__p___wargv`, `__p__environ`, `__p__wenviron`, `_get_initial_narrow_environment`, `_get_initial_wide_environment`, `_initialize_narrow_environment`, `_initialize_wide_environment`, `__p__fmode`, `__p__commode`, `_set_fmode`, `_get_fmode`, `_set_app_type`, `_set_new_mode`, `_set_invalid_parameter_handler`, `_configthreadlocale`, `_crt_atexit`, `_crt_at_quick_exit`, `_c_exit`, the three `onexit` table functions, `_fpreset`, `__daylight`, `__timezone`, `__tzname`, `_tzset`. The two tables are separate: `msvcrt.dll` does not provide `__stdio_common_vfprintf`, and `ucrtbase.dll` does not provide `__getmainargs`, as on Windows.
- `LoadLibraryA/W` and `FreeLibrary` exist for the built-in modules (`kernel32`, `msvcrt`, `ucrtbase`, their api-set names, any path to them, with or without `.dll`). `GetModuleHandle` accepts the same names and `GetProcAddress` on the handle finds that module's own exports. There is no reference count: `FreeLibrary` of a built-in succeeds and does nothing.

### Limits

- This step does not load DLL *files*; W5b below does.
- Every `api-ms-win-*` and `ext-ms-win-*` set other than the C runtime is served from the `kernel32` table. On Windows each set maps to a specific DLL (`kernelbase`, `ntdll`, `advapi32` and others); a function that is in the table but whose real set is different resolves here and would not there. For a program that works on Windows this cannot matter; for coverage reports it can make a program look runnable when it asks for something from `advapi32`, but only if that function is also in the table, and none are.
- The UCRT output options are the ones the MinGW headers pass: bit 1 (`0x1`) ignored, bit 2 (`0x2`) standard `snprintf` behaviour (the full length is returned, the buffer is always terminated), neither set the legacy `_snprintf` behaviour (`-1` on truncation, no terminator when the output fills the buffer exactly). `ucrt.exe` shows MinGW's `snprintf` and `_snprintf` land on the intended branches. The values come from the UCRT headers as I recall them and were not checked against a real `ucrtbase.dll`, which was not available. What bit `0x1` changes in Microsoft's implementation, if anything beyond what is described, is not known here and is not implemented.
- `__stdio_common_vsnprintf_s`, `__stdio_common_vsprintf_s`, the `scanf` family, wide printf and every wide function are not provided; programs that need them are reported by name. `printf` still has no floating point, so `%f` fails with `EINVAL` exactly as in W3.
- Command-line wildcard expansion (`_crt_argv_expanded_arguments`) is accepted and behaves as mode 1. The environment is empty. The time zone is `UTC` and `_tzset` does nothing. `__daylight`, `__timezone` and `__tzname` are provided as functions, which is how the UCRT headers declare them; the sample imports them but never calls them, so the call itself is checked only by the unit tests.
- The programs that run are MinGW programs. A program built by MSVC also needs `vcruntime140.dll` (`memset` intrinsics, `__CxxFrameHandler`, `_seh_filter_exe`) and no such program was available, so none has been run.

## W5b: loading DLL files

A program that imports a `.dll` of its own, or calls `LoadLibrary("name.dll")` for one, now gets it. The DLL is looked up in the directory the program was started from (`ram:/apps` from the shell), by file name only: `LoadLibraryA("C:\x\DllMath.dll")` finds `dllmath.dll` there, and a name without an extension gets `.dll`.

How it works, in `userland/pehost/modules.hpp` (header-only like the rest, so the host test runs the same text):

- **Handles.** A process still receives handles only through its start-up arguments, so the kernel now passes two: the program and, new, a directory handle with read and delegate rights. `launch_file(..., handle, &error, handle2)` moves both from the launcher's table into the child; `user_enter` puts the second in `rsi`, and `aphelion_main(u64 file, u64 directory)` is the new entry signature for every ring-3 program (`hello` ignores the second). The host reads a DLL with `file_open` relative to that handle, so it can open nothing outside that directory, and names that are only dots are refused before the call.
- **Mapping.** Each DLL is reserved with 64 KiB more than its image and aligned to 64 KiB, because the loader's relocator requires an aligned base. It is mapped, relocated, imports bound (recursively, to a depth of 4), TLS prepared and page protections applied, exactly as the program is.
- **Dependencies.** Each module keeps a reference count and a list of the modules it imports. Loading a DLL loads the DLLs it imports; releasing its last reference unloads it and then releases what it imported. At most 16 modules at once and 16 dependencies per module.
- **`DllMain` and TLS callbacks.** DLLs imported statically are attached in dependency order before the program's TLS callbacks and entry point, with `DLL_PROCESS_ATTACH` and a non-null `lpvReserved`. A DLL loaded by `LoadLibrary` is attached when loaded, with a null reserved argument. A `DllMain` that returns `FALSE` makes `LoadLibrary` fail with `ERROR_DLL_INIT_FAILED` (1114) and the DLL is unloaded again; for a static import the process is refused with status `0xC0000142`. `ExitProcess`, `exit` and returning from `main` detach every loaded DLL in reverse order with `DLL_PROCESS_DETACH` and a non-null reserved argument; `FreeLibrary` of the last reference detaches with a null one. `TerminateProcess` on the current process and `abort` end the process without detaching, as on Windows.
- **Exports.** `pe::find_export` (in `pe.hpp`) finds an export by name or ordinal, checking every table against the image. A forwarder (`dllmath.add`, `KERNEL32.Sleep`, or `DLL.#N`) is followed through other DLLs and the built-in modules up to 8 hops. `GetProcAddress` accepts names and ordinals; ordinals start at the directory's base, not at 1.
- **TLS.** A DLL with a TLS directory gets its own block and index (1 to 63) in the thread's slot array, which the compiler's `__declspec(thread)` accesses read through the TEB.
- **Process exit and other threads.** There is one thread, so no `DLL_THREAD_ATTACH` or `DLL_THREAD_DETACH` is ever delivered.

### Tests

`dllmath.dll` (exports a function, a variable and a forwarder), `dllchain.dll` (imports `dllmath.dll`, forwards into it and into `kernel32`, uses an explicit ordinal base), `dllplug.dll` (loaded at run time), `dllfail.dll` (`DllMain` returns `FALSE`) and `dyn.exe`, which imports `dllchain.dll` and exercises all of it, are MinGW builds in `tools/pe-samples/bin`. `dyn.exe` returns 7 when every check passes. They run in the host test, in the kernel self-test (also `dllmath.dll` started as a program is refused with `0xC000007B`) and from the shell with `run dyn.exe`.

- `pehost_lib_test` (375 checks) covers the manager with the real DLL files: loading, unloading, reference counts, forwarder chains including a loop and a missing target, ordinals, TLS indices, truncated and corrupted files, memory unmapped on unload, and that everything it unmaps is something it was given (a mutation that made `FreeLibrary` unmap the module table itself was found by this check and by nothing else).
- `pe::find_export` is run against 40,000 random corruptions of a real export directory without a crash or an out-of-range read.
- `peinfo` treats a DLL beside the program as providing what it exports, checking the DLL's own imports too; the coverage test shows `dyn.exe` runnable with its DLLs and blocked, with `dllchain.dll!add3` named, without them.

### Limits

- A DLL is found only in the program's own directory, by file name. There is no `PATH`, no system directory and no side-by-side manifest. `AddDllDirectory` is not provided and is reported as a missing import; `LoadLibraryExA/W` exists since W5c and refuses the flags that need a search path or a data-file mapping.
- A DLL must be relocatable (a `.reloc` table or position-independent), like programs. A DLL linked with `--disable-dynamicbase` and stripped of relocations is refused.
- Every protection run of an image is a separate mapping and a process may hold 64, so a program and its DLLs together are limited by that, not by memory. `dyn.exe` with four DLLs is well within it; a large program with many sections per DLL might not be.
- No data fix-ups beyond the import tables: the MinGW auto-import mechanism (pseudo-relocations) for data exported from a DLL is still not supported.
- DLL files are read whole, up to 16 MiB each; the copy is released as soon as the image is mapped.
- Not implemented: delay-load imports (the loader never reads that directory), `DisableThreadLibraryCalls`, `GetModuleFileNameA` for a DLL returns its lower-case file name without a directory, and `DLL_THREAD_*` notifications.
- The test DLLs are MinGW. W5c fetched real MSVC binaries, but they are programs and runtime libraries, not a plug-in DLL that imports the runtime and exports functions, so no MSVC-built DLL of that kind has been loaded yet.
- Verified in the sandbox: the host test under ASan and UBSan, the QEMU boots (NVMe with one and four cores, AHCI, VirtIO) and the shell session test. Not run on real hardware, and not run on Windows, so behaviours such as the exact order of `DllMain` calls follow the documented rules and the MinGW programs' own checks, not a comparison with a real loader.

## W5c: what a real MSVC program needs

Until now every program was built by MinGW. W5c fetches genuine Microsoft-toolchain binaries to see what they ask for, and implements what they need. `tools/real-binaries.sh <directory outside the repository>` downloads the Windows wheels of `ninja` (1.13.2, built with MSVC, C runtime linked in statically) and `msvc-runtime` (14.51, the redistributable DLLs) from PyPI, prints their SHA-256, runs `peinfo` coverage on them and runs `ninja.exe` under the host harness. The binaries are third-party, are never committed, and are executed only by the harness on the machine running the script (the harness runs the program's code natively, so use it only where that is acceptable).

What the real binaries showed:

- **A statically linked MSVC program asks kernel32 for far more than a MinGW one.** `ninja.exe` imports 136 functions, all from `kernel32.dll`: the C runtime inside it needs fiber-local storage, slim locks, locale and string classification, file APIs, `FormatMessage`, the process parameters in the PEB, SList functions and the exception-unwinding entry points. 116 of them are real now; 20 are in a second tier of stubs that exist so the program loads and fail with `ERROR_NOT_SUPPORTED` when called (processes, pipes, I/O completion ports, semaphores, jobs). `peinfo` reports those separately ("20 of them always fail") so "all provided" is never read as "will work".
- **The result.** The unmodified `ninja.exe` runs under the host harness: `--version`, `-h`, `-t targets`, `-t rules`, `-t commands` and `-n` (which reads `build.ninja` through the new file calls and stats the files through directory enumeration). A real build stops with `ninja: fatal: CreateIoCompletionPort: The request is not supported.` That message is the honest boundary: a build needs I/O completion ports, pipes and `CreateProcess`, which Aphelion's single-process, no-subprocess PE host cannot do.
- **`cmake.exe` from the same source imports 348 functions, 213 of them not provided:** 107 from kernel32 (mostly process, console and file-system calls that write), 38 from `ws2_32.dll`, 20 each from `crypt32.dll` and `advapi32.dll` (the registry and crypto), and smaller sets from `ole32`, `user32`, `oleaut32`, `shell32` and `dbghelp`. It is the next measuring stick, not a goal for W5c.
- **The real `msvcp140.dll` (the C++ standard library) imports 185 functions and 108 of them are not provided: 71 from the universal C runtime (locale, `strftime` helpers, string conversion), 35 from kernel32 (the thread pool, file information, `InitOnceExecuteOnce`, `WaitForSingleObjectEx`) and 2 from `vcruntime140`.** `peinfo` lists every one of them. It is the single largest piece left before C++ programs using the standard library can run, and it is an item on the roadmap.

What was added:

- `userland/pehost/win32x.hpp`, the second kernel32 layer, and `userland/pehost/vcrt.hpp`, the built-in `vcruntime140.dll` (`vcruntime140_1.dll` is folded into it by `pe::modules::canonical`): memory and wide-string helpers, `__std_exception_copy/destroy`, `type_info` comparison and hashing, the purecall and security-cookie failure paths, the frame handlers (present so a program with C++ code loads), `_CxxThrowException` and the unwinding entry points, which stop the process with the Windows status code and a message instead of returning.
- **Time.** `QueryPerformanceCounter/Frequency`, `GetTickCount(64)` and `GetSystemTimeAsFileTime` read a new platform hook. In the kernel that is `SYS_CLOCK` (33): a 32-byte record with uptime in milliseconds, wall time in milliseconds since 1970, the TSC frequency in kHz and two flags. The counter is the TSC, with the frequency the kernel measured, only when the kernel says it is usable: calibrated against a real timer rather than assumed, and the CPU reports an invariant TSC (CPUID 0x80000007 bit 8). Otherwise the counter is the 10 ms tick count at 1000 Hz. A wall clock the kernel does not trust is not reported, and the time functions then use uptime.
- **Files.** `CreateFileA/W` (read only, `OPEN_EXISTING`), `ReadFile`, `GetFileSizeEx`, `SetFilePointerEx`, `GetFileType`, `GetFileAttributes(Ex)`, `CloseHandle` and `FlushFileBuffers`, up to 32 open at once, handles 0x100 upward. `FindFirstFile(Ex)`, `FindNextFile` and `FindClose` list the program's directory with `*`, `?` and `*.*`, up to 8 searches. Everything is relative to the same directory handle that serves DLLs (it now has the Enumerate right too); anything that writes, or names a path, is refused with the error Windows would give.
- **Process data.** `PEB->ProcessParameters` points at a real `RTL_USER_PROCESS_PARAMETERS` (standard handles, command line, image path, current directory `\`), which the MSVC start-up code reads; before this, `ninja.exe` crashed at exit through a null pointer. An environment table of 32 variables, case-insensitive, behind `Get/SetEnvironmentVariableA/W` and `GetEnvironmentStringsW`.
- **Locking and fibers.** Fiber-local storage (128 slots, the destructor callback runs on `FlsFree`), SRW locks and condition variables, and the SList functions. With one thread nothing can release a lock or signal a condition, so a wait that cannot end (an infinite wait, taking a held exclusive lock) stops the process with `STATUS_POSSIBLE_DEADLOCK` rather than hanging, and a timed wait sleeps and returns `ERROR_TIMEOUT`.
- **Other.** `GetModuleHandleExW`, `GetModuleFileNameW`, `LoadLibraryExA/W`, `RtlPcToFileHeader`, locale, `CompareStringW/Ex`, `LCMapStringW/Ex` (case mapping only), `GetStringTypeW` (ASCII classes), `VerSetConditionMask` and `VerifyVersionInfoA` (answers as Windows 10 build 19045, workstation), `FormatMessageA` for the common system messages, and console queries that fail the way a redirected handle does.

`sysio.exe` is a MinGW program that uses the new calls on the machine itself: it measures a 120 ms sleep with the performance counter, the tick count and the system time, reads its own file (the `MZ` and `PE` signatures, the size, a negative seek, closing twice), finds itself with `FindFirstFile("*.exe")`, checks the missing-file and write-denied errors, environment, FLS and an SRW lock. It returns 6 when every check passes, and runs in the host test, the kernel self-test and with `run sysio.exe`. A ring-3 blob, `clockcall`, tests the syscall itself: the record, the flag bits, time moving forward, a straddling or kernel-space output pointer being refused with nothing written, and that `rdtsc` is allowed in ring 3.

### Tests

- `pehost_lib_test` grew from 375 to 535 checks, 160 of them for this work: every function above, with a fake clock, in-memory files and a fake directory. Hooks that return short reads, fail part way, or are missing are tried, as are all limits (32 files, 8 searches, 128 FLS slots, 32 variables), both signs of the version comparison and every `VerifyVersionInfoA` condition, and the failure exits in forked children (deadlock, `RaiseException`, unwinding, purecall, stack overrun, thrown C++ exception, `terminate`). 17 single-line mutations of the new code were each caught: case-sensitive environment, an overflowing tick scale, a read loop that stops after one chunk, FLS callback skipped, a split surrogate pair, a changed condition hierarchy, a seek check that never fires, a file left open when the table is full, `wcsrchr` returning the first match, `type_info` always equal, an exception message shared when it should be copied, and the rest.
- The userland host test checks the clock record layout, the flag bits and the usable-counter rule over all eight combinations.
- `make test-pehost` runs `sysio.exe` under the harness and compares `docs/pe-supported.txt` (now 336 entries, 20 marked as always failing).

### Limits

- The counter is only as good as the kernel's idea of an invariant TSC: it checks the CPUID bit and that the calibration was measured, not that the counters of different cores agree. On a machine where they do not, a thread that moves between cores could see time step backwards. The QEMU runs used here are software-emulated, which cannot offer an invariant TSC, so only the 1000 Hz tick fallback has been run; the TSC path is verified by the host harness (which has its own clock) and by the unit tests, not on a CPU that reports it. Resolution on the fallback is the 10 ms kernel tick.
- Files are read only and live in one directory. There is no current directory beyond `\`, no creation, no writes, no overlapped I/O, `GetFileAttributesEx` reports no times (`FindFirstFile` reports the modification time as all three), and a directory is reported as not found by `GetFileAttributes` and `CreateFile`.
- No process creation, pipes, I/O completion ports, semaphores, events beyond what W3 had, thread pool or jobs: those APIs load and then fail. `ninja.exe` cannot build anything for that reason.
- No exceptions. `RaiseException`, SEH unwinding and C++ `throw` stop the process with the Windows status; `__try`/`__except` blocks and C++ `try`/`catch` never catch anything. A program that uses them only on error paths runs until the first error.
- The environment table is separate from `getenv` in `msvcrt` (a variable set through one is not visible through the other). It now starts with the variables the launcher passes (see W5d.1), but only through `GetEnvironmentVariable` and the process block.
- Locale support is `en-US` only, comparison and case mapping cover ASCII, and `GetStringTypeW` classifies ASCII. A program that sorts or transforms non-ASCII text will get the wrong answer instead of a failure.
- A lock or condition wait that no thread could end is an error, which is correct today (one thread) and will be wrong when threads exist.
- Verified in the sandbox only: the host test under ASan and UBSan, the QEMU boots and the shell session test. The real MSVC binaries ran under the Linux host harness, not under Windows and not on Aphelion itself. Behaviour is checked against the documentation and the programs' own checks, not against a real Windows.

## W5d: closing the accumulated limits

Every section above ends with a list of limits, and by W5c they add up to more than any one of them. W5d is a milestone to close them, ordered by how many programs each one blocks: standard input, arguments and environment from the shell; threads and real synchronisation in the host; a file system with subdirectories and writes; the rest of the C runtime (guided by `peinfo --coverage` on the real `msvcp140.dll`); structured and C++ exceptions; loader memory (merged mappings, pseudo-relocations, delay-load); and clock precision checked on hardware. A limit is closed when its line leaves this document and a test fails without the fix. The end-to-end check is `ninja.exe` running a real build under `tools/real-binaries.sh`. The inventory and the order are in the roadmap kept with the project.

### W5d.1: arguments, environment and standard input (done)

Until now a program started from the shell had a fixed command line (`pe.exe`), no environment and no input. The shell now hands every program the same start-up message, whatever kind of program it is, and each executor translates it into its own world. The message is described in `docs/RING3.md` ("The start-up contract"); the Windows half is this:

- `pehost` receives the message instead of two raw handles. The program file, the program directory and standard input are handles in the message; the arguments become the command line with the Microsoft quoting rules (`cmdline::join`, the inverse of the parser the C runtime uses, round-tripped in the tests including empty arguments, embedded quotes and trailing backslashes), `argv[0]` is the program name and the module path, and each `NAME=value` becomes an environment variable.
- `ReadFile` on the standard input handle reads from the pipe the shell filled (a new `Runtime::read_stdin` hook); at the end of input it succeeds with zero bytes, a host with no input behaves as it did before, and an error from the hook is `ERROR_BROKEN_PIPE`.
- `argv.exe` (MinGW) prints its arguments, command line, module name, two environment variables and everything read from standard input. The host harness can be given a command line, `--env NAME=value` and `--stdin text`, so the same program is checked on the host, in the kernel self-test and from the shell.
- A program is found with or without `.exe` (`argv one two`); a native program takes the same message (`echo`, written for this, and `hello`, which now checks its own).

Tests: the start-up message has 40 checks in `userland_host_test` (round trips, every refusal, the size limits, 5 single-line mutations of the encoder and decoder, of which two survived the first round and led to a simplified check and a new test); `pehost_lib_test` went from 535 to 548 checks (the join round trips, checked against 6 single-line mutations of `join`, and standard input); `helm_host_test` has 13 new checks for program names, arguments, pipelines, status and wildcards; the kernel self-test runs five programs through the contract and four refusals that must leave no handle or process behind; `tools/ci-shell.sh` runs `run echo`, a bare program name, `argv` with and without a pipe, and a table piped into a native program; `make test-pehost` runs `argv.exe` under the harness and compares its whole output.

Limits that remain, on purpose for now: standard output still goes through the console sink, not a handle, so a program's output cannot be redirected to a file or a pipe except as the text the shell captures; `fgets`, `fread`, `getchar` and `_read` on `stdin` are not provided by the built-in C runtime, so a program that reads input through them still fails to load (kernel32 `ReadFile` works); the message is one 256-byte channel message, so arguments and environment together are at most about 240 bytes and 15 arguments; standard input is at most 64 KiB and is delivered whole before the program starts, so a program cannot be fed interactively; the shell passes one variable (`SHELL=helm`), not its bound names; there is no current-directory change.
